## Stated purpose

Make the silent-delivery-failure class of bug observable — when an agent's
reply makes it into the session transcript but never reaches the external
channel (e.g. stale channel context after a model fallback), operators
should learn about it via stderr, and internal callers should see it via
the function's return value.

## In scope (after slim — 2026-05-08; NEEDS REWRITE post-refactor)

**NOTE (2026-05-09): NEEDS FULL REWRITE against new `sendDurableMessageBatch` API.**

Upstream closed #57843 as superseded and landed a broader refactor:
- `sendDurableMessageBatch(...)` is now the canonical API
- `deliverOutboundPayloads(...)` is now **deprecated** and guarded by
  `check:deprecated-message-api` (wired into `check:architecture`) — production
  code CANNOT use it. Our current diff fails this architecture check.

New `sendDurableMessageBatch` return shape (enriched):
```ts
send.status: "sent" | "suppressed" | "partial_failed" | "failed"
send.payloadOutcomes: Array<{
  status: "sent" | "suppressed" | "failed";
  reason?: "cancelled_by_message_sending_hook" | "empty_after_message_sending_hook" | "no_visible_payload";
  // + cancellation reason/metadata on suppressed outcomes
  // + delivered prefix on partial_failed
}>
```

What this PR still contributes on top of upstream:
- `deliveryStatus` structured object (`{ requested, attempted, succeeded, hadPartialFailure?, error? }`)
  derived from `send.status` and `send.payloadOutcomes`
- Stderr warning `[delivery] delivery requested but not completed: <reason>`
  — only fires when `send.status === "failed"` or `"partial_failed"`;
  `"suppressed"` (hook-cancelled) emits NO warning (false positive problem solved)
- Tests covering status-tracking paths against the new API

What is NOW moot:
- `try/catch` wrapping `deliverOutboundPayloads` — new API surfaces errors via `send.status`
- `hadPreflightError`, `deliveryAttempted`, `deliveryThrewError` flags
- `deliverySucceeded` backward-compat field — already in upstream's return value
